# 3. Спецификация агентов

## Сводная таблица

| # | Агент | Роль (одна) | Вход | Выход | Инструменты (≤ 5) | Критерий завершения | Статус |
|---|---|---|---|---|---|---|---|
| 0 | **Orchestrator** | Понять запрос и составить план | `user_query` | `task_plan` | — | Валидный `TaskPlan`, прошедший правила (есть `data_agent`; для forecast/health есть `forecast_agent`) | ✅ A2 |
| 1 | **Data Agent** | Собрать и проверить данные о воздухе и погоде | `task_plan` | `data_package` | `geocode_city`, `fetch_air_quality`, `fetch_weather`, *`fetch_station_data`* | Город найден и оба набора данных загружены (`ok`/`partial`) **или** после повтора возвращён `error` с причиной | ✅ A2 |
| 2 | **Forecast Agent** | Прогноз среднесуточного PM2.5 на 0–3 дня | `data_package` | `forecast_result` | `run_ml_forecast`, `get_cams_forecast` | Для каждой целевой даты выбран доступный источник (ml/cams/blend) и уверенность | ✅ A2 |
| 3 | **Analyst Agent** | Объяснить причины уровня загрязнения | `forecast_result` или `data_package` (+ данные из TaskState) | `analysis_report` | `compute_correlations`, `detect_inversion`, `compare_with_seasonal_norm` | 1–4 фактора, каждый подтверждён числом из результатов инструментов; тренд определён | ✅ A2 |
| 4 | **Health Agent** | Рекомендации для здоровья с учётом группы | `analysis_report` / `forecast_result` | `health_advice` | `get_who_guidelines`, `get_aqi_category` | Уровень риска и ≥ 2 рекомендации для группы пользователя, сравнение с нормой ВОЗ | A4 |
| 5 | **Reporter Agent** | Написать итоговый ответ пользователю | `health_advice` (+ результаты из TaskState) | `final_report` | — | Ответ содержит ключевые числа прогноза, источники и дисклеймер | A4 |
| 6 | **Critic Agent** | Проверить ответ на ошибки и соответствие данным | `final_report` | `critic_verdict` | `verify_numbers`, `check_required_parts` | Вердикт: `approved` или список замечаний с агентом для доработки | A4 |

Роли не пересекаются. Orchestrator только планирует, Data Agent только добывает данные
(без прогнозов), Forecast Agent только прогнозирует (без советов), Analyst Agent объясняет
«почему», Health Agent отвечает «что делать», Reporter Agent формулирует ответ, а Critic Agent
проверяет и ничего не пишет сам.

## Общий принцип: LLM решает, код считает

У каждого агента есть **решение LLM** (`decision_model`) и **факты от инструментов**.
Метод `finalize()` объединяет их и проверяет правила. Числа, которые увидит пользователь
(значения PM2.5, категории, доли пропусков), считает код, а не LLM. Поэтому LLM не может
«придумать» значение. Если решение LLM нарушает правила (например, выбран источник,
недоступный для даты), агент получает замечание и исправляется (не больше 2 раз).

---

## 0. Orchestrator ✅

- **Роль:** классифицировать запрос и составить план. Никакой предметной работы.
- **Вход:** `UserQuery {text}`.
- **Выход:** `TaskPlan {intent, city, days_ahead, user_group, steps[], rationale}`.
- **Инструменты:** нет.
- **Решает LLM:** тип запроса (forecast / current / explain / health / out_of_scope), город,
  горизонт, группа пользователей, состав агентов.
- **Проверяет код:** шаги приводятся к каноническому порядку и избавляются от повторов;
  `data_agent` обязателен; для forecast/health обязателен `forecast_agent`; если город не указан,
  подставляется «Алматы»; для `out_of_scope` план пустой.
- **Критерий завершения:** валидный план, прошедший правила.
- **Ошибки:** невалидный план → замечание и повтор (≤ 2), затем `AgentError` с понятным текстом.
- **В Ассайнменте 4:** вдобавок получает `critic_verdict` и решает, кого отправить на доработку
  (не больше 2 раундов).

## 1. Data Agent ✅

- **Роль:** собрать почасовые данные о загрязнении и погоде для города и оценить их качество.
- **Вход:** `TaskPlan` (город, `days_ahead`, intent).
- **Выход:** `DataPackage` со ссылками на данные (`air_ref`, `weather_ref`), долей пропусков,
  последним наблюдением, источником (`network` / `cache` / `stale_cache`) и списком проблем.
- **Инструменты:**

| Инструмент | Что делает | Источник |
|---|---|---|
| `geocode_city(name)` | координаты города (только Казахстан) | Open-Meteo Geocoding API |
| `fetch_air_quality(lat, lon, past_days, forecast_days)` | почасовые PM2.5, PM10, NO2: история + прогноз CAMS; кладёт таблицу в TaskState, возвращает сводку | Open-Meteo Air Quality API |
| `fetch_weather(lat, lon, past_days, forecast_days)` | температура, влажность, ветер, давление, осадки, высота пограничного слоя | Open-Meteo Forecast API |
| *`fetch_station_data(lat, lon)`* (A4) | измерения ближайших наземных станций для сверки с CAMS | OpenAQ API |

- **Решает LLM:** как искать город (если «Нур-Султан» не найден → «Астана»), глубину истории
  (не меньше 8 дней для модели) и горизонт загрузки, повторять ли запрос при ошибке, итоговый статус.
- **Проверяет код:** статус `ok`/`partial` возможен только при реально загруженных данных;
  если пропусков > 20%, статус понижается до `partial`; использование устаревшего кэша
  попадает в `issues`.
- **Критерий завершения:** данные загружены, или после одного повтора возвращён `status=error` с причиной.
- **Ошибки:** HTTP-сбои → 3 попытки с паузой → устаревший кэш → понятная ошибка; ошибка
  инструмента приходит LLM как результат с `is_error`, и агент сам решает, что делать.

## 2. Forecast Agent ✅

- **Роль:** прогноз среднесуточного PM2.5 на сегодня и до 3 дней вперёд.
- **Вход:** `DataPackage` и `days_ahead` из плана (через TaskState).
- **Выход:** `ForecastResult` — по каждой дате прогноз ML с 80%-интервалом, прогноз CAMS,
  итоговое значение, источник, категория AQI и уверенность, плюс метрики модели.
- **Инструменты:**

| Инструмент | Что делает |
|---|---|
| `run_ml_forecast(days_ahead)` | собственная модель (HistGradientBoosting, 18 признаков) — см. [06_forecast_model.md](06_forecast_model.md) |
| `get_cams_forecast(days_ahead)` | среднесуточный прогноз физической модели CAMS из данных Data Agent |

- **Решает LLM:** для каждой даты — какому источнику доверять (`ml`, `cams`, `blend`)
  и насколько уверен прогноз; краткое обоснование.
- **Считает код:** сами прогнозы, итог (`ml` / `cams` / среднее), категорию по шкале AQI,
  проверку, что выбранный источник доступен для даты, и потолок уверенности по расхождению
  источников (|ML − CAMS| / среднее: < 25% → high, 25–60% → medium, > 60% → low). LLM может
  поставить уверенность ниже потолка, но не выше. Такой случай был в реальном прогоне на
  `gemini-3.5-flash-lite`: модель написала «разница менее 25%» при фактических 36%. Теперь
  такой ответ отклоняется, и агент исправляет его сам.
- **Критерий завершения:** для всех целевых дат есть корректный выбор источника.
- **Ошибки:** нет модели или признаков → инструмент возвращает причину, и LLM выбирает CAMS;
  нет данных от Data Agent → `AgentError`, диспетчер останавливает задачу с понятным сообщением.

## 3. Analyst Agent ✅

- **Роль:** объяснить, *почему* загрязнение такое: метеорологические и сезонные факторы.
  Прогнозов и советов не даёт.
- **Вход:** `ForecastResult` (если в плане есть прогноз) или `DataPackage`; почасовые данные берутся
  из TaskState по ссылкам, история — из `data/training_daily.csv`.
- **Выход:** `AnalysisReport {drivers[{factor, evidence, strength}], trend, vs_seasonal_norm_pct, summary,
  history_city, monthly_pm25}`.
- **Когда запускается:** Orchestrator включает его в план для вопросов «почему» (intent `explain`).
- **Инструменты:**

| Инструмент | Что делает |
|---|---|
| `compute_correlations(days)` | корреляция PM2.5 с ветром, пограничным слоем, температурой и влажностью по часам за последние дни, плюс средняя погода в самые грязные (верхние 25%) и самые чистые (нижние 25%) часы |
| `detect_inversion()` | признаки застоя по дням: ночной минимум пограничного слоя < 100 м и ночной ветер < 3 км/ч; средний PM2.5 в дни застоя и в остальные дни |
| `compare_with_seasonal_norm()` | средние по месяцам из истории 2023–2026 (PM2.5, пограничный слой, ветер, температура), норма текущего месяца, отклонение последних 3 дней от нормы, тренд |

- **Решает LLM:** какие факторы главные, насколько они сильны, как объяснить это простым языком.
- **Считает и проверяет код:** все числа в инструментах, тренд (изменение > 15% — рост или снижение)
  и отклонение от нормы. В `evidence` каждого фактора должно быть хотя бы одно число, которое
  реально вернули инструменты (с учётом округления). Иначе ответ отклоняется, и агент исправляется.
  Это защита от выдуманных объяснений.
- **Пример на реальных данных (Алматы, 06.10.2026):** в самые грязные часы пограничный слой был
  в среднем 78 м, в самые чистые — 573 м. Дней застоя оказалось 6 из 9, средний PM2.5 в них 15.1,
  в остальные дни 10.9. Сезонный профиль: январь 37.5 мкг/м³ при слое 59 м, июль 14.4 при 607 м.
- **Если города нет в истории:** берётся ближайший из 8 городов (`nearest_history_city`), расстояние
  указывается в результате.
- **Критерий завершения:** 1–4 фактора с подтверждёнными числами; тренд определён.

## 4. Health Agent (A4)

- **Роль:** перевести уровень загрязнения в практические рекомендации для группы пользователя.
- **Вход:** `ForecastResult` / `AnalysisReport`, `user_group` из плана.
- **Выход:** `HealthAdvice {category, risk_level, who_guideline_exceeded, groups_at_risk[], recommendations[]}`.
- **Инструменты:** `get_who_guidelines(pollutant)` — нормы ВОЗ 2021 (локальная база);
  `get_aqi_category(pm25)` — категория и стандартные рекомендации EPA.
- **Критерий завершения:** определён уровень риска и есть ≥ 2 рекомендации для группы.
- **Ограничение:** не ставит диагнозов; в рекомендациях обязательна ссылка на врача для групп риска.

## 5. Reporter Agent (A4)

- **Роль:** написать понятный ответ на русском по структурированным результатам.
- **Вход:** результаты Data, Forecast, Analyst и Health Agent (из TaskState).
- **Выход:** `FinalReport {answer, key_numbers{}, sources[], disclaimer}`.
- **Инструменты:** нет: работает только с уже проверенными данными, новых фактов не добывает.
- **Критерий завершения:** ответ отвечает на вопрос пользователя и содержит ключевые числа,
  источники и дисклеймер.

## 6. Critic Agent (A4)

- **Роль:** независимая проверка итогового ответа.
- **Вход:** `FinalReport`.
- **Выход:** `CriticVerdict {approved, issues[{severity, field, message}], revise_agent}`.
- **Инструменты:** `verify_numbers(answer)` — каждое число в тексте сверяется с `TaskState.results`
  (допуск ±0.1); `check_required_parts(answer)` — проверка, что есть город, дата, категория
  и дисклеймер.
- **Критерий завершения:** вынесен вердикт. Если найдены major-ошибки, Orchestrator отправляет
  `revise_agent` на доработку (не больше 2 раз), иначе пользователь получает ответ с пометкой
  о непройденной проверке.
